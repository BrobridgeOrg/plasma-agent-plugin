# 代碼名稱缺漏時的候選補充

產出資料時（mview、pview、BI），若 Plasma 知識庫或實際字典結果缺少代碼名稱、翻譯或描述，且 LLM
能提出有用的補充，**主動提出具體候選並詢問使用者，不直接填入資料**。兩種模式都適用；
差別只在先查哪裡、核准後怎麼放進 SQL。

## 1. 先查現有知識與字典

模型訓練知識是候選依據，不等於已查核的來源事實；先完成現有知識與字典查找，
區分「知識未收錄」與「資料字典欄位缺值」，不以 LLM 略過可用來源。

- **一般模式**：`get_column_card` 的綁定值域、`get_value_domain` 與 `search_value_candidates`（見 [一般模式的查法](standard.md)）。
- **進階模式**：`read_knowledge`（`mode` 為 `definition`）讀該欄位或概念的實體層附註「值的意義（代碼 → 意思）」（見 [進階模式的查法](advanced.md)）。
  附註沒有時，這是知識缺口：照下節提出候選；另外告訴使用者，要讓之後的查詢也有這些名稱，須補文件或回答缺口（[補齊缺口](../../plasma-fill-gaps/SKILL.md)）。

## 2. 提出候選並取得確認

- 補充僅限已查核識別值的名稱、翻譯與描述。不能據此虛構來源表、欄位、關聯、
  業務紀錄或指標數值；需要變更篩選、類別分組或指標口徑時，另行說明並確認。
- 核對完整識別值、所屬系統、適用版本及語言，不混用不同系統或版本的定義；
  保留識別值的有效格式，不擅自展開、截短或合併。
  識別不明或有多個解讀時先釐清，無把握的名稱保留缺漏。
- 集中列出待確認表：識別鍵／系統／版本、目前缺漏及候選補充值，供使用者確認。
  不要求在確認表或產出資料標記「LLM 訓練知識候選」或「未經外部來源核實」。
  有實際查核來源時可附來源，不虛構引用或宣稱知道訓練資料出處；補充仍須確認才套用。
- 同時說明套用位置與範圍，例如「只補本次 mview 的缺漏類別名稱，原始識別值、
  人次、排名及既有字典名稱保持不變」。詢問使用者接受全部、指定項目或保留原值。
  等待對具體清單的明確確認；一般報表授權、同步確認、沉默均不視為補充核准。
  等待時可繼續不依賴補充的查核與驗證，不執行包含未核准候選的 SQL 或產出。
- 確認後只套用核准項目，原始來源優先、補充僅填缺漏；交付保留補充依據與核准
  範圍，讓名稱能追溯。候選清單、版本或套用範圍變更時重新確認；未確認或拒絕時
  保留原始代碼／缺值並如實說明，不影響其餘已授權工作。
- 本次結果補充不等於寫回來源資料庫或永久更新 Plasma 知識庫。

## 3. 核准後放進 SQL

核准的映射一律放在 mview，pview 仍只做最後篩選，BI 不另寫名稱替換或類別合併邏輯；
BI 發現相同缺漏時也回到這裡，不自行補值。

- **一般模式**：依 [一般模式的 sql-path](sql-path/standard.md) 第 4 點「核准的名稱／描述補充」，以 `VALUES` CTE 保存映射並 LEFT JOIN。
- **進階模式**：編譯出的 SQL 原封不動，在外層以 `CASE` 轉換：
  `SELECT r.<其他欄位>, …, CASE r.<代碼欄> WHEN '<代碼>' THEN '<核准名稱>' … ELSE r.<名稱欄> END AS <名稱欄> FROM (<編譯出的 sql>) r`
  （逐欄列出、不用 `r.*`，避免名稱欄重複；原本沒有名稱欄時 `ELSE NULL`，名稱欄為新增的欄）。這是 [進階模式 sql-path](sql-path/advanced.md) 外層允許的轉換，不加連接、條件或分組，不改變列數。

驗證補充前後筆數、人次、分子／分母與排名一致，僅核准的缺漏文字改變。
mview 描述與交付欄位來源須標明哪些值來自「使用者確認的補充映射」，並記錄
候選依據、版本及核准範圍；仍無對應者保留原碼／缺值。此確認不取代同步確認。
