# 進階模式的 sql-path：由 `compile_query` 編譯並補洞

進階模式的 SQL 全部由程式依已發布的知識產生：agent 把使用者的問題轉成「報表請求」，`compile_query` 回 SQL；
知識沒說清楚的地方是洞：使用者回答、確認要讀什麼之後由 agent 補上，補齊了才拿到 SQL。只用已發布的知識；Commit 區還沒發布的規則不會出現在 SQL 裡。
不自己從頭寫 SQL，也不改動程式產生的部分。

用的是讀取群的工具：`read_knowledge`、`read_schema` 與 `compile_query` 只讀已發布的知識與 schema；文件分析用的工具屬於寫入群，這裡不用。
任何工具的回覆說內容未完（附 `cursor`、`has_more` 為 true）時，先以 `read_tool_reply` 帶那個 `cursor` 讀到 `has_more` 為 false，再呼叫其他工具。

## 1. 找到指標與概念，組成請求

1. 先分析問題需要哪些知識：要算什麼、算在誰身上、有哪些業務邏輯與限定，逐項列出來，再一項一項找。
2. 用 `read_knowledge`（`mode` 為 `search`）以使用者的用語找已發布的指標（measure）或分類（class）、屬性與實體，再用 `mode` 為 `definition` 讀定義，判斷它是不是**完整符合**使用者要的意思：
   - **完整符合**：直接用這個概念，它的定義與對應都會帶進來；編譯不出來的部分會成為洞。
   - **不完全符合**：一定列出來問使用者，附上差在哪裡，由使用者決定，你不自己決定、也不自行加條件。同時用 `mode` 為 `dependencies` 讀它引用的概念：它不完全符合、但它引用的概念完全符合時，用引用的概念組成新概念。相似的概念也是搜尋的索引，順著它找相關的概念。
   - **找不到**：問使用者這個概念的定義，再搜尋現成的子概念來組合（第 1.1 節）。
   - 使用者的說法對到不只一個概念時，把候選的中文名稱與定義列給使用者選。
3. 把問題拆成請求的各部分：
   - 要算的指標（`measure`，已發布的指標）；題目要把某個已發布的值加總、計數、取平均或最大最小時，用 `aggregate`（`fn` 為 sum、count、count_distinct、min、max 或 mean，`value` 為那個值；計數一個分類或實體的成員時給 `of`）；或要列出的分類或實體與附帶的屬性（`select`）；
   - 分組（`dimensions`）：依實體、依屬性（時間可加 `bucket`：day、week、month、quarter、year，都是西元曆），或依一組分類（`classes`，其他歸入 `other`）；
     農曆年、會計年度、公司自訂的週期是知識：先找表達它的已發布概念（例如「會計年度」屬性），找不到時寫成 `ask` 分組；不用相近的西元 `bucket` 代替；
     分組與篩選的屬性用已發布的概念名稱。題目寫的是欄名（例如 `plant_id`）時，選指標所計那個實體的屬性：每個實體各有自己的「工廠」等屬性；
   - 篩選（`filters`）：只計某分類，或某屬性比較某值。題目隱含的母體條件（例如只計已過帳、排除測試客戶）也是篩選：先找表達它的已發布分類；
   - 截點（`as_of`）與期間（`window`）；使用者說民國年時換成西元（民國年＋1911，月日相同），例如民國 113 年是 2024-01-01 起到 2025-01-01 前，並在回報中說明換算。
     要建成 view 時另依第 4 節；
   - 輸出欄名（`columns`：概念 → 欄名），使用者指定欄名時照用。題目也要比率指標的分子、分母時，把它們計的分類或加總的值也寫進 `columns`，同一份 SQL 會一起輸出，不分開查詢。
4. 題目需要、但找不到任何已發布概念、也組不出來（第 1.1 節）的分組或條件，是知識庫缺的知識：在那個分組或篩選裡用使用者的說法寫 `"ask"`（例如分組 `{"ask": "工廠", "as": "plant_id"}`、篩選 `{"ask": "已過帳"}`）。`ask` 只寫屬性本身的短名稱；它屬於指標所計的那個實體，問題會自己帶上那個實體的名稱；編譯時那裡會留一個洞，問使用者它存在哪個欄位或怎麼判斷。

### 1.1 用現成概念組新概念

知識庫沒有完整符合的概念，但現成的概念或葉概念組得出來時，像堆積木一樣組：

1. 把要用的積木列給使用者確認：「這個是不是由 A、B 組成？還要加什麼限定？」積木可以是上層概念，也可以是葉概念。
2. 使用者確認後，在請求帶 `define`：`name`（以 `session.` 開頭）、`term`（使用者的說法）、`of`（這個概念是哪個實體的列）、`value`（是一個值時寫它的種類，例如 `Number`）、`when`（用已發布概念與欄位寫的規則本體，列是 `?x`，值是 `?v`），之後請求就用這個 `name`。
3. 已發布的概念在等一個沒有定義的概念時（洞的 `where` 是那個概念），要補的是它本身：`name` 用那個概念自己的名稱，`of` 用它的實體，引用它的概念都會讀到這個定義。另取 `session.` 名稱補不到那個洞。
4. 每塊積木的全部限定都會成立，也帶著自己的對應，不用重寫。缺的概念沿用洞補上。不同實體的積木要用它們之間的關聯概念接起來，接不起來時回覆會說明，改好請求再送。
5. `reading` 會寫出定義的內容，也會提醒：「各自只要有一筆符合，不一定是同一筆」「在它之後才套用」「條件互斥」。這些原樣給使用者看；不是使用者要的，就改定義。
6. `define` 或 `bind` 改變後是另一個請求：舊的 `compile_id` 與洞都不算數，先不帶 `fills` 重新編譯，再依新的洞與 `compile_id` 補。
7. 工具清單有 `submit_answer` 時，以它保存使用者的定義，依 [補齊缺口](../../../plasma-fill-gaps/SKILL.md) 第 4 節寫回 Commit 區，發布後大家都能用；沒有時告訴使用者：這次的定義只用在這份 SQL。

積木組不出來的分組或條件，才用下面第 3 節的 `ask`。

## 2. 編譯並請使用者核對

呼叫 `compile_query`。`complete` 為 false 時回覆只有 `reading`、`holes` 與 `expects`，沒有 `sql`；`complete` 為 true 時才有 `sql`。回覆中：

- `reading`：這份 SQL 算的是什麼，原樣給使用者看，請使用者確認就是他要的。
- `holes`：知識沒說的地方。每個洞有 `question`（要問使用者的話）、`reason`、`expects`（要補的是條件、值或幾欄的列）與 `gaps`（對應的知識庫缺口）。
- `basis`：依據的規則、對應與假設（例如「以封閉世界讀強否定」）；假設也告訴使用者。
- `release`：依據的發布版本。

回覆是請求錯誤時，改正請求再送，直到編譯出結果：

- 概念不存在：回覆的 `suggestions` 列出每個名稱的相近概念（欄名先列出對應到那個欄位的概念）；用 `read_knowledge` 讀它們的定義，選對的一個，回到第 1 節組好請求。
- 回覆說某概念 `is not a measure`：它是每一列的值，沒有發布的指標。題目要加總或計數它時改用 `aggregate`（同樣的分組與篩選）；要逐列列出時改用 `select`（`of` 為它的實體、`attributes` 含它與要分組的屬性）。

## 3. 補洞

1. 把每個洞的 `question` 問使用者，一次問完；附上 `reading` 讓使用者知道問的是哪一部分。用使用者聽得懂的業務說法問，SQL、洞的 `expects` 與內部名稱留給自己；使用者通常只回答一個欄位、一個值或一句說明，這樣就夠了。
2. 用 `read_knowledge`、`read_schema` 與 `expects` 把使用者的話對到要讀的表與欄位：`read_schema` 查表與欄位，`expects` 說片段能讀哪些來源。`read_schema` 的搜尋回 `has_more` 為 true 而沒有 `cursor` 時，是符合的太多：縮小搜尋的字詞再查。
3. 向使用者提議要讀的東西，業務意思在前，例如「我打算用已分配金額（payment_allocation.allocated_minor）的加總，對嗎？」。使用者確認之後才補；使用者說不對時，依他的話換一個候選再問。
4. 使用者確認後：
   - 工具清單有 `submit_answer`（寫入群）時，以它保存使用者的原話（問題與回答），之後可以依 [補齊缺口](../../../plasma-fill-gaps/SKILL.md) 補進知識庫，下次就不再有這個洞；
   - 工具清單沒有 `submit_answer` 時，照樣用使用者的回答補這份 SQL 的洞，並告訴使用者：這次的回答只用在這份 SQL，沒有存回知識庫，要讓之後的查詢也用到，須由有寫入權限的人在缺口頁回答或補文件；
   - 洞有 `expects.leaf` 時，它是一個還沒對應到欄位的葉概念：以 `read_schema`（`mode` 為 `candidates`，`concept` 為洞的 `where`）搜尋實體層，把候選欄位用業務說法列給使用者選，選定後在請求帶 `bind`（`concept`、`column` 為 `db.table.column`、`answer` 為使用者的原話），不用寫片段。分類沒有欄位可選，缺的是定義時用 `define`（第 1.1 節）；`bind` 只回答值在哪一欄，換算或單位的洞還在，要另外補；
   - 只有 `bind` 與 `define` 都表達不了時，才依回答把洞寫成一段 SQL：一個運算式，或用括號包起來的一個子查詢，只用 `expects` 列出的別名與欄位，或 schema 裡的表與欄位，寫法照 [Plasma SQL 寫法](plasma-sql.md)。有洞時回覆沒有 SQL：表名照 `read_schema` 查到的寫（例如 `"manufacturing"."ar_invoice"`），`expects.rows` 列到的實體一律讀它的 `from`；單位的洞填一個正數，存放值乘上它就是宣告的單位；
   - 洞的 `expects.rows` 給出那個實體的資料列（`from`：已套用截點與版本的那段查詢，以別名 `t` 讀）與一列的身分（`identity`）：洞要的是列時，以 `SELECT <identity> AS c1, … FROM <from> t` 為底，再依使用者說的欄位接上需要的表；
   - 以 `compile_query` 送出同一個請求並帶 `fills`（洞的 id → SQL 片段）、`answers`（洞的 id → 使用者的原話）與 `compile_id`（給出這些洞的那次編譯回覆的值）。其餘部分由程式產生；補齊後回傳的 `sql` 是實際要執行的那份，別名與結構可能和寫片段時不同：通常是最佳化過的版本（`optimized` 為 true），Plasma 驗證不過時退回照規則逐段寫的版本（`optimized` 為 false）。
5. 關聯洞（`reason` 為 `relation_unverified` 或 `relation_refuted`）是知識庫有這條關聯、但程式這次不讀它：文件寫了兩張表怎麼連接，Plasma 還沒驗證、無法驗證，或抽樣驗證時推翻了。洞的 `relation` 帶著這條關聯的完整內容：兩端的表（`from`、`to`）、連接欄位（`on`）、經過的表（`through`）與條件（`condition`）、基數與文件寫的原文（`stated`、`qualifier`）、出處（`doc`、`line`），以及狀態與原因（`status`、`use`、`reason`、`detail`；推翻時有抽樣筆數 `checked_rows` 與違反筆數 `violations`）。
   - 把洞的 `question` 原樣問使用者；問句已經說明是哪條關聯、為什麼這次沒讀，以及推翻時的違反筆數。
   - 使用者確認依這條關聯讀取時，依 `relation` 自己寫出那一段：洞要的列以 `expects.rows` 的 `from` 與 `identity` 為底（`c1` 是成員的身分，屬性的洞另有 `c2` 為值），照 `relation` 的 `on` 連到 `to` 的表；有 `through` 時依序經過那些表，並套用 `condition`。以 `fills` 再編譯。
   - 工具清單有 `accept_relationship`（寫入群）時，以它保存使用者的確認（`relationship` 為 `relation.id`，附上問題與使用者的原話）：確認進 Commit 區，發布後之後的編譯就會直接讀這條關聯。`relation.reason` 為 `join_unknown` 時，問句會問文件寫的連接鍵各是哪個欄位：以 `complete_relationship` 保存使用者給的欄位（`on` 寫成 `欄位 = 另一張表的欄位`），發布後 Plasma 驗證補好的關聯。
   - 工具清單沒有這兩個工具時，照樣用使用者的確認補這份 SQL，並告訴使用者：這次的確認只用在這份 SQL，要讓之後的查詢也直接用，須由有寫入權限的人確認。
   - `relation_refuted` 的關聯被 Plasma 推翻，每份 SQL 都會再出現這個洞：每次都照問句問使用者，不沿用上次的回答。
   - 編譯可能要等 Plasma 就地驗證需要的關聯（每次最多幾條，抽樣執行）；照常等待 `compile_query` 回覆，驗證通過的關聯不再是洞。
6. 回覆的 `complete` 為 true 才有 SQL；`validation.valid` 為 false 時這份 SQL 不能執行。錯誤在你寫的片段：依錯誤自己修改片段再送，直到通過，不必問使用者。錯誤不在片段：這是編譯器的問題，不要改片段，如實告訴使用者並附上錯誤。
7. 使用者說不知道時，如實告訴使用者缺什麼資訊、目前無法算出，列出缺的項目；不自行假設數值或規則。

`complete` 為 true 時交給呼叫技能的是回覆的 `sql`（實際執行的那份）、`reading`（已列出每個回答）、結果與 `basis`、`release`；回答由 `reading` 呈現，不另外轉述。
使用者要的呈現方式（民國年、日期格式、排序、欄名）編譯結果沒有提供時，在外面包一層
`SELECT …呈現的欄位… FROM (<編譯出的 sql，原封不動>) r`：外層只轉換、排列已算好的欄位，不加條件、連接或分組；
內層的條件、連接、分組與計算都是知識庫的定義，一律不改。外層做了什麼要告訴使用者。
使用者核准的代碼名稱補充也放在這一層，以 `CASE` 轉換（[代碼名稱的候選補充](../code-names.md)）。

## 4. 要建成 mview 時

mview 會定期同步，同一份 SQL 要每次同步都算出當下的結果；pview 再以參數篩選期間。所以請求與一次性報表不同：

- **不帶 `as_of`**：版本化的表（每鍵多版）不帶截點時，每次同步都讀每個鍵的最新版；帶了 `as_of`，每次同步都停在那個時間點。
  指標的截點由已發布的知識決定時（`basis` 有該常數），截點是固定值，告訴使用者；知識缺截點而編譯出截點的洞時，問使用者是否要固定截點，不自行填當下時間。
- **不帶 `window`**：期間交給 pview。把期間要依的時間寫成分組（`dimensions` 的時間屬性加 `bucket`，例如 month），mview 保存各期結果，pview 以參數篩選期別欄位。
  `bucket` 的粒度依報表的期別決定；跨期不可加總的指標（去重計數、比率），依 [建立 pview 技能](../../../plasma-create-view/SKILL.md) 第 1 節另外提供較大的期別。
- 篩選只放業務定義的母體條件；使用者每次查詢會變的條件（工廠、期間）改成分組，留給 pview 的參數。
- 補洞照第 3 節；補的是固定的業務定義，不要寫入只對這次查詢成立的值。

建立後，進階模式會自動把這個 mview 的 SQL 轉成知識（view 的欄位與來源欄位的關係），不經 Commit 頁；
建立、修改 view 或 mview 不算 schema 變更，不需要重新對應。
