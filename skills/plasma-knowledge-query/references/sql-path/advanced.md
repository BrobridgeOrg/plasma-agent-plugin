# 進階模式的 sql-path：由 `compile_query` 編譯並補洞

進階模式的 SQL 全部由程式依已發布的知識產生：agent 把使用者的問題轉成「報表請求」，`compile_query` 回 SQL；
知識沒說清楚的地方是洞：agent 先依已有的事實推測補上、把 SQL 做出來，再把每一筆推測列給使用者核對（第 3 節）。只用已發布的知識；Commit 區還沒發布的規則不會出現在 SQL 裡。
不自己從頭寫 SQL，也不改動程式產生的部分。

用的是讀取群的工具：`read_knowledge`、`read_schema` 與 `compile_query` 只讀已發布的知識與 schema；文件分析用的工具屬於寫入群，這裡不用。
任何工具的回覆說內容未完（附 `cursor`、`has_more` 為 true）時，先以 `read_tool_reply` 帶那個 `cursor` 讀到 `has_more` 為 false，再呼叫其他工具。

## 1. 找到指標與概念，組成請求

1. 先分析問題需要哪些知識：要算什麼、算在誰身上、有哪些業務邏輯與限定，逐項列出來，再一項一項找。
2. 用 `read_knowledge`（`mode` 為 `search`）以使用者的用語找已發布的指標（measure）或分類（class）、屬性與實體，再用 `mode` 為 `definition` 讀定義，判斷它是不是**完整符合**使用者要的意思。
   `definition` 的回覆為每個概念附上實際生效的樣子（`effective`）：`read_from` 一行一筆寫它讀自哪個欄位或哪些列，加上這些欄位與表的附註（含條件式讀法）與所屬群組的規則（附來源）。要理解一個概念實際怎麼算，讀這一段與它的規則；缺口標 `incomplete` 時，`parts` 列出缺在哪些組成概念，接著讀它們的定義。
   - **完整符合**：直接用這個概念，它的定義與對應都會帶進來；編譯不出來的部分會成為洞。
   - **不完全符合**：記下差在哪裡，用 `mode` 為 `dependencies` 讀它引用的概念：它不完全符合、但它引用的概念完全符合時，用引用的概念組成新概念（第 1.1 節）。相似的概念也是搜尋的索引，順著它找相關的概念。組不出來時，用定義與文件的事實最支持的讀法繼續，把差異記成一筆推測（第 3.1 節）。
   - **找不到**：搜尋現成的子概念來組合（第 1.1 節）；組不出來時寫成 `ask`（下面第 4 點）。
   - 使用者的說法對到不只一個概念時：定義、對應或文件的事實分得出是哪一個，就用它並記成一筆推測；事實分不出來時，把候選的中文名稱與定義列給使用者選。
3. 把問題拆成請求的各部分：
   - 要算的指標（`measure`，已發布的指標）；題目要把某個已發布的值加總、計數、取平均或最大最小時，用 `aggregate`（`fn` 為 sum、count、count_distinct、min、max 或 mean，`value` 為那個值；計數一個分類或實體的成員時給 `of`）；或要列出的分類或實體與附帶的屬性（`select`）；
   - 分組（`dimensions`）：依實體、依屬性（時間可加 `bucket`：day、week、month、quarter、year，都是西元曆），或依一組分類（`classes`，其他歸入 `other`）；
     農曆年、會計年度、公司自訂的週期是知識：先找表達它的已發布概念（例如「會計年度」屬性），找不到時寫成 `ask` 分組；不用相近的西元 `bucket` 代替；
     分組與篩選的屬性用已發布的概念名稱。題目寫的是欄名（例如 `store_id`）時，選指標所計那個實體的屬性：每個實體各有自己的「門市」等屬性；沒有任何概念對到的欄位，`read_schema` 會列出它在 `compile_query` 用的名稱（標示 `stored`）；
     要知道一個指標能依什麼分組時，用 `read_knowledge`（`mode` 為 `dimensions`，`predicate_names` 為那個指標、彙總或實體）：它列出計數的實體到得了的實體、路徑與各自的屬性與分類；`blocked` 是分組時會開洞問的。只分組題目問的；
     用值識別的實體（各資料庫各自編碼、沒有一張表列出全部成員）與它的分類（`exp.class.<名>`）也像實體與屬性一樣分組、篩選：`read_knowledge` 的 `search` 在 `values.matches` 標出使用者的詞對到全部成員、某個成員、某個分類或某個分類值；一個詞對到好幾個時問使用者是哪一個。對照不到的值歸入「其他」，`reading` 會寫明用了哪些對照；
   - 篩選（`filters`）：只計某分類，或某屬性比較某值。題目隱含的母體條件（例如只計已付款、排除贈品）也是篩選：先找表達它的已發布分類；
   - 截點（`as_of`）與期間（`window`）；使用者說民國年時換成西元（民國年＋1911，月日相同），例如民國 113 年是 2024-01-01 起到 2025-01-01 前，並在回報中說明換算。
     要建成 view 時另依第 4 節；
   - 輸出欄名（`columns`：概念 → 欄名），使用者指定欄名時照用。`select` 的 `columns` 也列出要輸出的屬性；題目要成員的鍵（編號）時，用鍵欄的名稱列進去，每一列仍是一個成員。題目也要比率指標的分子、分母時，把它們計的分類或加總的值也寫進 `columns`，同一份 SQL 會一起輸出，不分開查詢。
4. 題目需要、但找不到任何已發布概念、也組不出來（第 1.1 節）的分組或條件，是知識庫缺的知識：在那個分組或篩選裡用使用者的說法寫 `"ask"`（例如分組 `{"ask": "門市", "as": "store_id"}`、篩選 `{"ask": "已付款"}`）。`ask` 只寫屬性本身的短名稱；它屬於指標所計的那個實體，問題會自己帶上那個實體的名稱；編譯時那裡會留一個洞：它存在哪個欄位或怎麼判斷，照第 3 節補。

### 1.1 用現成概念組新概念

知識庫沒有完整符合的概念，但現成的概念或葉概念組得出來時，像堆積木一樣組：

1. 依定義與文件的事實決定用哪些積木，記成一筆推測：「我把這個讀成由 A、B 組成，限定是…」。積木可以是上層概念，也可以是葉概念。
2. 在請求帶 `define`：`name`（以 `session.` 開頭）、`term`（使用者的說法）、`of`（這個概念是哪個實體的列）、`value`（是一個值時寫它的種類，例如 `Number`）、`when`（用已發布概念與欄位寫的規則本體，列是 `?x`，值是 `?v`），之後請求就用這個 `name`。
3. 已發布的概念在等一個沒有定義的概念時（洞的 `where` 是那個概念），要補的是它本身：`name` 用那個概念自己的名稱，`of` 用它的實體，引用它的概念都會讀到這個定義。另取 `session.` 名稱補不到那個洞。
4. 每塊積木的全部限定都會成立，也帶著自己的對應，不用重寫。缺的概念沿用洞補上。不同實體的積木要用它們之間的關聯概念接起來，接不起來時回覆會說明，改好請求再送。
5. `reading` 會寫出定義的內容，也會提醒：「各自只要有一筆符合，不一定是同一筆」「在它之後才套用」「條件互斥」。這些原樣給使用者看；不是使用者要的，就改定義。
6. `define` 或 `bind` 改變後是另一個請求：舊的 `compile_id` 與洞都不算數，先不帶 `fills` 重新編譯，再依新的洞與 `compile_id` 補。
7. 已發布的概念和使用者說的定義不完全一樣時（少了限定、範圍或截點），編譯完成也不用它，不改編譯結果，也不等人修編譯器：看它引用的概念，引用的概念符合就用 `define` 組一個新概念；組不出來時用 `aggregate` 的 `ask`（或分組、篩選的 `ask`）照使用者的定義問。相似的概念是找積木的線索，不是答案。
8. 使用者核對過的定義才寫回（第 3.1 節）。

積木組不出來的分組或條件，才用上面第 4 點的 `ask`。

## 2. 編譯

呼叫 `compile_query`。`complete` 為 false 時回覆只有 `reading`、`holes` 與 `expects`，沒有 `sql`；`complete` 為 true 時才有 `sql`。回覆中：

- `reading`：這份 SQL 算的是什麼。原樣放進給使用者的說明（第 3.1 節），不改寫。
- `holes`：知識沒說的地方。每個洞有 `question`（要問使用者的話）、`reason`、`expects`（要寫什麼，見第 3 節）與 `gaps`（對應的知識庫缺口），以及已發布知識對它說的：`gap_details`、`related` 與 `column_notes`（第 3 節第 1 點）。
- `basis`：依據的規則、對應與假設（例如「以封閉世界讀強否定」）；假設也告訴使用者。另有幾類各自列出，附來源，連同結果告訴使用者：
  - `group_rules`：指標屬於某個概念群組時，群組的規則自動套用：範圍條件（只計哪些列，逐部分套用）、事件時間（只寫 `bucket` 的分組、`window` 與 `as_of` 沒指名時間時用它）、指標慣例（分母為零、空值、截點含不含，補指標沒寫明的）。請求自己的篩選或分組讀到同一欄或同一概念時，範圍條件的那一部分交給請求，不再套用。使用者明說不要某條規則時，請求帶 `scopes`（`{規則名: "off"}`）取消整條。規則彼此不一致時會成為洞，問使用者用哪一條；
  - `conditional_readings`：一欄依同一列的條件分情況讀（例如批發列的數量以箱計、其餘以個計），SQL 已套用；
  - `table_standings`：讀到已退役的表（停用或舊系統鏡像）或受限的欄位；
  - `sensitive_columns`：輸出欄讀到來源標為敏感的欄位，連同類別告訴使用者。Ophion 不遮罩輸出。
- `release`：依據的發布版本。

回覆是請求錯誤時，改正請求再送，直到編譯出結果：

- 概念不存在：回覆的 `suggestions` 列出每個名稱的相近概念（欄名先列出對應到那個欄位的概念）；用 `read_knowledge` 讀它們的定義，選對的一個，回到第 1 節組好請求。
- 回覆說某概念 `is not a measure`：它是每一列的值，沒有發布的指標。題目要加總或計數它時改用 `aggregate`（同樣的分組與篩選）；要逐列列出時改用 `select`（`of` 為它的實體、`attributes` 含它與要分組的屬性）。

## 3. 補洞：先依事實推測，再請使用者核對

1. **先找事實。** 先讀洞自己帶的知識：`gap_details`（每個缺口的全文：值從哪裡來、哪裡還沒確認）、`related`（這些缺口與概念說明點名的表、它們的欄位、點名的欄與彼此的關聯）與 `column_notes`（依 `db.table.column` 列出：值的意義、NULL 的意義、單位、讀法、格式、這一欄怎麼算出、已退役的表與它的標準表、來源禁止的用途、敏感欄位）。補法照這些寫。
   還不夠時，用 `read_knowledge`（定義、依賴、附註）、`read_schema`（表、欄位、欄位的附註、候選欄位）與洞的 `expects`、`gaps` 找出它該讀什麼：`read_schema` 查表與欄位，`expects.t` 是這個洞所說的那一列 t 的表。`read_schema` 的搜尋回 `has_more` 為 true 而沒有 `cursor` 時，是符合的太多：縮小搜尋的字詞再查。
2. **依事實決定怎麼補。**
   - 事實指向一個讀法：用它補，記下一筆推測：知識庫缺什麼、補成什麼、依據是什麼（哪個概念的定義、哪個欄位的附註、哪份文件的哪一行）。
   - 幾個讀法都說得通而事實分不出來，或找不到任何依據：這個洞問使用者。用使用者聽得懂的業務說法問洞的 `question`，附上 `reading`，SQL、`expects` 與內部名稱留給自己；要問的一次問完。其他的洞照常推測，不等這一題。
   - 被資料推翻的關聯（`relation_refuted`）一律先問（第 4 點）。
3. **補上。**
   - 洞有 `expects.leaf` 時，它是一個還沒對應到欄位的葉概念：以 `read_schema`（`mode` 為 `candidates`，`concept` 為洞的 `where`）搜尋實體層的候選欄位；附註與定義分得出是哪一欄就選它，分不出來時把候選用業務說法列給使用者選。選定後在請求帶 `bind`（`concept`、`column` 為 `db.table.column`、`answer` 為依據），不用寫運算式。分類沒有欄位可選，缺的是定義時用 `define`（第 1.1 節）；`bind` 只回答值在哪一欄，換算或單位的洞還在，要另外補；
   - 只有 `bind` 與 `define` 都表達不了時，才為洞寫**一個運算式**，寫法照 [Plasma SQL 寫法](plasma-sql.md)。`expects.write` 說要寫什麼：
     - `value`：`expects.t` 那張表的一列 t 的值，用 t 的欄位寫（欄位在 `t_columns`，種類在 `kind`），例如 `date_trunc('month', t."paid_at")`；
     - `condition`：哪些列 t 算在內，例如 `t."state" = 'PAID'`；有 `expects.u` 時，寫 t 與 `u` 那張表的一列怎麼對上，例如 `t."store_id" = u."store_id"`；
     - 沒有 t、只有 `aliases` 的值或條件，用那些別名寫；`rows` 只出現在整份報表都是洞的時候：寫一個用括號包起來的查詢，輸出 `expects.columns` 那幾欄。
   - 要用到其他列時（彙總明細、取最新一筆、比對區間），在運算式裡放一個只回一欄、以 t 對應的子查詢，條件則用 `EXISTS`，例如 `(SELECT sum(l."amount") FROM "sales"."order_items" l WHERE l."order_id" = t."order_id")`。表名照 `read_schema` 查到的寫，程式會照這份查詢的截點與版本讀它；不要在子查詢裡再包一層讀 t 的子查詢；取某時點以前最新的一筆用 `max_by(值, 時間)`，不用 `ORDER BY … LIMIT 1`（這兩種 Plasma SQL 都不支援，會回「correlated subquery is not supported」）。
   - 列的身分、`c1` 與 t 的資料列都由程式寫，運算式裡不寫；單位的洞填一個正數，存放值乘上它就是宣告的單位；
   - 每一列的值（`value`，有 t）隨那一列而定：不讀 t 的任何東西的運算式會被拒。只有使用者的回答說每一列都是同一個值時，才填那個值，並在請求帶 `constant`（洞的 id → true）；
   - 補洞讀到來源禁止某種用途的欄位（例如計算金額時讀舊價目表的單價）會被拒，回覆指出改讀哪張標準表，照它改；
   - `expects.write` 為 `choice` 的洞用選擇回答，不寫運算式：請求帶 `choose`（洞的 `where` → `expects.choices` 之一）重新編譯，不帶 `fills`；之後還缺的會成為新的洞，依新的 `compile_id` 補。選哪一個同樣先看事實，事實分不出來時問使用者；
   - 以 `compile_query` 帶 `fills`（洞的 id → 運算式）、`answers`（洞的 id → 這一筆的依據）與 `compile_id`（給出這些洞的那次編譯回覆的值）再送；`compile_id` 指名那次的請求，不用把請求重送一次。同一個 `compile_id` 已接受的補洞會保留：再送時只帶新的或改正的，沒送的洞沿用原本的補法；要清掉某個洞的補法，送空字串 `""`。回覆的 `filled_from` 標出每個已補的洞來自這次或沿用。`answers` 與 `bind` 的 `answer` 寫這一筆補的依據：使用者說的照錄原話；推測的以「代理推測：」開頭，寫補成什麼與依據。`reading` 會列出每一筆，所以看得出哪些是推測。其餘部分由程式產生；補齊後回傳的 `sql` 是實際要執行的那份，別名與結構可能和寫運算式時不同：通常是最佳化過的版本（`optimized` 為 true），Plasma 驗證不過時退回照規則逐段寫的版本（`optimized` 為 false）。
4. **關聯洞**（`reason` 為 `relation_unverified` 或 `relation_refuted`）是知識庫有這條關聯、但程式這次不讀它。洞的 `relation` 帶著這條關聯的完整內容：兩端的表（`from`、`to`）、連接欄位（`on`）、經過的表（`through`）與條件（`condition`）、基數與文件寫的原文（`stated`、`qualifier`）、出處（`doc`、`line`），以及狀態與原因（`status`、`use`、`reason`、`detail`；推翻時有抽樣筆數 `checked_rows` 與違反筆數 `violations`）。
   - `relation_unverified`：文件寫了兩張表怎麼連接，Plasma 還沒驗證或無法驗證。依 `relation` 自己寫出那一段，記成一筆推測，依據是文件的原文與出處。
   - `relation_refuted`：Plasma 抽樣驗證時推翻了這條關聯。把洞的 `question` 原樣問使用者（問句已說明是哪條關聯、為什麼沒讀與違反筆數），使用者確認依它讀取後才補；每份 SQL 都會再出現這個洞，每次都問，不沿用上次的回答。
   - 補法：照洞的 `expects.write` 寫一個運算式。有 `expects.u` 時，依 `relation` 的 `on` 寫 t 與 u 怎麼對上；有 `through` 時用 `EXISTS` 經過那些表，並套用 `condition`。以 `fills` 再編譯。
   - `relation.reason` 為 `join_unknown` 時，文件沒有寫連接鍵各是哪個欄位：兩張表的鍵與欄位附註指得出來時照它推測；指不出來時問使用者。
   - 編譯可能要等 Plasma 就地驗證需要的關聯（每次最多幾條，抽樣執行）；照常等待 `compile_query` 回覆，驗證通過的關聯不再是洞。
5. 回覆的 `complete` 為 true 才有 SQL；`validation.valid` 為 false 時這份 SQL 不能執行。錯誤在你寫的運算式：依錯誤自己修改再送，直到通過，不必問使用者。錯誤不在運算式：這是編譯器的問題，不要改運算式，如實告訴使用者並附上錯誤。
6. 知識允許一個成員有好幾個值的地方，SQL 讀成每個成員一個值，執行時會檢查。執行時查詢說某個成員有不只一個值：問使用者每個值都要算（`aggregate` 帶 `each` 為 true，或把那個屬性放進 `select` 的 `each`，一個值一列，再編譯一次），還是只取哪一個。

### 3.1 列給使用者核對

每一筆推測都要讓使用者看到，並由使用者決定對不對。什麼時候給：

- **一次性報表**：SQL 完成就執行，交出結果時一起給。
- **要建成 mview、pview 或 BI**：建立之前給，使用者核對完才建立（[建立 pview 技能](../../../plasma-create-view/SKILL.md) 的建立前確認）。

分成兩段，知識庫已經寫明的依據另外照 `basis` 與 `release` 列，不放進這兩段：

- **需要你核對的**：每筆推測一列，寫知識庫缺什麼、我補成什麼、依據是什麼、這一筆不對時結果的哪裡會變。業務意思在前，例如「知識庫沒說『折價券折抵金額』存在哪一欄；我用 order_items.coupon_amount 的加總，依據是這一欄的附註寫『折價券折抵的金額（元）』；不對的話各期金額都會變」。
- **我自己決定的**：不改變定義的選擇，例如欄名、排序、日期與數字的呈現、期別怎麼切、外面包的那一層。

使用者核對之後：

- **說對的**：這時才寫回知識庫，只保存使用者確認的那幾筆，每筆帶他確認時的原話；還沒核對的推測不保存。
  - 關聯用 `accept_relationship`（`relationship` 為 `relation.id`，附上問題與使用者的原話）：確認立即生效，之後的編譯就讀這條關聯，下一次 commit 一併記錄。連接鍵由使用者給出時用 `complete_relationship`（`on` 寫成 `欄位 = 另一張表的欄位`），它進 Commit 區，發布後 Plasma 驗證補好的關聯。
  - 經 `compile_query` 補上的洞（運算式或 `choose` 的選擇）：用 `keep_fills`，`compile_id` 是接受這些補洞的那次編譯，`keep` 每筆寫洞的 id（`hole`）與使用者確認的原話（`words`），選擇洞另帶 `choice`，`question` 是使用者原本的問題。程式能直接轉成知識的（類別的條件、只讀一欄的值、文字欄的讀法、對照表、換算的選擇）寫成 Commit 區的產物；轉不了的（讀別張表的子查詢、運算式、知識庫沒有的概念）留在回答文件，列成待補項目，由 [補齊缺口](../../../plasma-fill-gaps/SKILL.md) 寫成知識。回覆逐洞列出產物或待補項目。
  - 沒有經過補洞、你自己依讀到的規則寫的 SQL 裡的推測：用 `keep_agreed`，`question` 是使用者的問題，`confirmed` 每筆寫使用者的原話（`words`）、知識庫缺什麼（`lacked`）、你用的 SQL 條件或運算式照寫（`sql`）與推測的依據（`rests_on`）。每筆列成待補項目，由補齊缺口寫成知識。
  - 葉概念的 `bind` 與 `define` 組成的新概念：以 `submit_answer` 保存問題與使用者的原話，依補齊缺口第 4 節寫回 Commit 區。
  - 寫回的內容都進 Commit 區，使用者在 Commit 頁發布後，之後的查詢就不再有這些洞。
  - 工具清單沒有 `keep_fills` 這些寫入群的工具時，告訴使用者：這次的確認只用在這份 SQL，要讓之後的查詢也用到，須由有寫入權限的人在缺口頁回答或補文件。
- **說不對的**：依使用者的話重補：以同一個 `compile_id` 只送改正的那幾個洞，`answers` 改成他的原話；報表重新執行。
- **說不知道的**：報表保留這一筆，結果標明它是未經確認的推測；要建立 mview、pview 或 BI 時，由使用者決定要不要照這一筆建立。
  使用者回答了一般情況、只對某種邊界情況說不知道時（例如資料互相衝突、日期無效），先看那個情況真的發生時會怎樣：補上的值一列只能有一個，真的有兩個時查詢會失敗並說出是哪個概念；讀不成日期的文字也會讓查詢失敗。這類情況不會算錯：照已確認的部分補完、執行，回報時寫明這個情況還沒有規則，發生時查詢會報錯。會靜默算進結果的情況才是要核對的推測。

`complete` 為 true 時交給呼叫技能的是回覆的 `sql`（實際執行的那份）、`reading`（已列出每一筆補上的內容）、結果與 `basis`、`release`，以及上面兩段清單；補上的內容由 `reading` 呈現，不另外轉述。
使用者要的呈現方式（民國年、日期格式、排序、欄名）編譯結果沒有提供時，在外面包一層
`SELECT …呈現的欄位… FROM (<編譯出的 sql，原封不動>) r`：外層只轉換、排列已算好的欄位，不加條件、連接或分組；
內層的條件、連接、分組與計算都是知識庫的定義，一律不改。外層做了什麼列在「我自己決定的」。
使用者核准的代碼名稱補充也放在這一層，以 `CASE` 轉換（[代碼名稱的候選補充](../code-names.md)）。

## 4. 要建成 mview 時

mview 會定期同步，同一份 SQL 要每次同步都算出當下的結果；pview 再以參數篩選期間。所以請求與一次性報表不同：

- **不帶 `as_of`**：版本化的表（每鍵多版）不帶截點時，每次同步都讀每個鍵的最新版；帶了 `as_of`，每次同步都停在那個時間點。
  指標的截點由已發布的知識決定時（`basis` 有該常數），截點是固定值，告訴使用者；知識缺截點而編譯出截點的洞時，問使用者是否要固定截點：這一題沒有事實可推測，不填當下時間。
- **不帶 `window`**：期間交給 pview。把期間要依的時間寫成分組（`dimensions` 的時間屬性加 `bucket`，例如 month），mview 保存各期結果，pview 以參數篩選期別欄位。
  `bucket` 的粒度依報表的期別決定；跨期不可加總的指標（去重計數、比率），依 [建立 pview 技能](../../../plasma-create-view/SKILL.md) 第 1 節另外提供較大的期別。
- 篩選只放業務定義的母體條件；使用者每次查詢會變的條件（門市、期間）改成分組，留給 pview 的參數。
- 補洞照第 3 節；補的是固定的業務定義，不要寫入只對這次查詢成立的值。推測在建立前列給使用者核對（第 3.1 節），核對完才建立。

建立後，進階模式會自動把這個 mview 的 SQL 轉成知識（view 的欄位與來源欄位的關係），不經 Commit 頁；
建立、修改 view 或 mview 不算 schema 變更，不需要重新對應。
