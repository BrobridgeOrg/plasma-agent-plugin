# 補齊缺口

全程使用台灣繁體中文；工具名稱、欄位名稱、符號與網址保留原樣。

開始前先確認連線：依 [連結 Plasma 與診斷](../plasma-mcp-setup/SKILL.md) 完成授權，以 `whoami` 核對 workspace 與 `knowledge:write`，並以 `run_status` 記下 `setup.commit_page`（使用者確認發布的頁面）。

**本 skill 只用於進階模式。** 核對 scopes 之前，先依 [查 Plasma 知識庫](../plasma-knowledge-query/SKILL.md) 判斷模式：工具清單沒有 `compile_query`、但有 `search_knowledge` 時，這個系統是一般模式（建立後不會改變）。這時告訴使用者：這個系統是一般模式，plugin 目前沒有一般模式的補缺口流程，待補的問題請在 Plasma 介面處理。然後結束本 skill：不要求使用者重新授權，也不改用其他工具或自己寫 SQL 繞過。兩組工具都沒有時，依連結 Plasma 與診斷的「診斷」處理。

待補項目是知識庫還缺的東西：缺定義、缺引用的文件、原文有歧義、對應沒做完，或等使用者裁決。補上的產物進 Commit 區，使用者發布後才生效。

**本 skill 只寫流程，以及和使用者之間的事。** 產物怎麼提交，讀 MCP：`read_task`（`target` 為 `document`）的協定，與每個工具自己的說明；每一項怎麼補，讀它自己的 `closes_with`。回覆帶 `next_step` 時照它做。

補齊的依據有三種：使用者的回答、文件寫明的內容（已在系統裡的與之後上傳的），或使用者授權你自行讀取的來源（資料表的列、schema、其他系統）。三種都沒有的，照 `question` 問使用者，或留在待補：定義與選擇由使用者或文件給。

## 主流程

1. 呼叫 `pending_items` 列出待補項目（第 1 節）。
2. 決定這次處理哪些項目（第 2 節）：有依據的自己補，需要使用者的整理成問題一次問。
3. 一項一項補（第 3、5 節）；使用者回答了，照第 4 節轉交後再補。
4. 都走完一次後，再查一次 `pending_items`，請使用者發布（第 7 節）。

## 1. 查詢待補項目

呼叫 `pending_items`；只看某份文件時帶 `document`。每一項讀這些：

- `item_id`：這一項的 ID，開頭說明它是哪一種（第 3 節）；轉交使用者的回答時帶它。
- 出處（`evidence`）、缺什麼（`missing`）、它在等的引用（`references`）、受影響的規則（`rules`），以及要問使用者的問題（`question`，有的話）。
- `closes_with`：一句話說明由哪個工具、哪個產物補上，依據去哪裡找。**補一項時照它做。**
- `fill`：誰來補。
  - `evidence`：知識庫或已轉交的回答已有依據，`fill_basis` 指出是什麼，直接補。
  - `retry`：系統處理失敗，再做一次，沒有要問的。
  - `person`：系統裡找不到依據。先查一次（第 2 節），仍沒有就問使用者。
  - `later`：要等系統之後支援，沒有要問的；最後如實告訴使用者，`fill_basis` 是原因。
- `how`：帶 `how` 的項目不靠提交產物補上。`how` 說明它由什麼補，例如使用者在 Commit 頁裁定、`bind_term`，或回報使用者。照 `how` 做。

只是在等另一項的上層概念，摺疊在它等的那一項底下：那一項的 `dependents` 是等它的項數，補齊那一項，它們就一起完成。要看全部時帶 `all`，每項再列出它等的 `waits_on`。

回覆的 `definition_rulings` 是使用者在 Commit 頁對同一概念兩份定義的裁定，不是待補項目；其中標示要重新裁定的，請使用者回 Commit 頁處理。

## 2. 決定處理範圍

- **自己補的**：`fill` 為 `evidence` 與 `retry` 的項目。
- **先查再決定的**：`fill` 為 `person` 的項目，先依 `closes_with` 說的地方查一次，通常是以 `lookup_knowledge` 查 `missing` 的用語或相關的表。別份文件寫明了缺的內容時，以那份文件為依據補；查不到就照 `question` 問使用者。
- **問使用者**：把要問的整理後一次問，每題附上出處，讓使用者知道問的是哪一段。
- **結束條件**：範圍內的項目都走完一次，並再查一次 `pending_items` 確認。

## 3. 碰到各種項目時

每一項的 `closes_with` 或 `how` 已經寫了怎麼補。這裡說的是各種項目的意思，以及什麼時候找使用者。

- **產物留下的缺口**（`reported-gap:…`）：原文說不清楚，或依賴別處的內容，提交時留在產物上的缺口。依它的 `status`：
  - `awaiting_resolution`：在等引用的文件。請使用者依 [文件分析](../plasma-document-analysis/SKILL.md) 上傳並分析那份文件；`missing` 顯示對象已存在時直接補。
  - `gap`：缺定義或缺資訊。請使用者說明並轉交（第 4 節），或由寫明它的文件補。
  - `ambiguity`：引用對得上多份文件。請使用者指定是哪一份，轉交後補。
- **概念沒有定義**（`gap:…`）：定義用同一個符號寫出。概念自己的文件寫了定義，就在那份文件上補；由使用者說明時，轉交後在回答文件上補。
- **計算或統計缺資訊**（`dag:…`）：先查原文有沒有寫，有寫就在宣告它的那份文件上補。沒寫才照 `question` 問使用者；轉交回答後，仍在宣告它的那份文件上補。上層概念因子概念不完整而列出時，補根本原因那一項。
- **文件有新版本**（`document:…`、`reconfirm:…`）：新版本還沒有產物，或有已發布的產物等著重新確認。依文件分析的「文件改版」處理。
- **對應**（`mapping:…`）：
  - 對應還沒做或沒做完：請使用者同意後執行對應（文件分析的「請使用者決定是否執行對應」）。
  - 對應留下資料對應的缺口：照 `question` 請使用者提供資料來源或確認對應，轉交回答後再執行一次對應。
  - 概念要讀的表或欄位不在 schema 裡：問使用者是表還沒匯入，還是文件用了另一個名稱。表匯入後再執行一次對應，文件不用重新分析。
- **規則檢查**（`rule-check:…`）：後到的概念讓這條規則可能被讀錯，`question` 說明原因。修正規則，或說明規則為何正確。
- **覆蓋檢查**（`coverage:…`）：下一版發布後，查詢會在這裡缺一塊；`affected` 列出受影響的指標。宣告或讀到所缺概念的文件有寫，就在那裡補；沒寫時照 `question` 問使用者並轉交。
- **確認過的補洞**（`answer-fill:…`）：使用者在報表確認、以 `keep_fills` 或 `keep_agreed` 保存的內容。回答文件已有使用者的原話與依據，直接依它補，不用再問使用者。
- **探測衝突**（`probe-conflict:…`）：資料抽樣的結論和文件寫的不一樣。照 `question` 把兩邊列給使用者，請他決定以哪一個為準，再轉交（第 4 節）。
- **讀法待寫**（`read-pending:…`）：在讀法陳述所在的那份文件上補，沒有要問的。
- **事實衝突**（`metadata-contract:…`、`metadata-value:…`、`constant-contract:…`、`constant-value:…`、`versioning:…`）：不同文件說法不一。請使用者到 Commit 頁的「事實衝突」區裁定；讀了這些事實的規則（`metadata-reader:…`）在裁定後的下一次發布帶入。
- **綁定**（`binding:…`）：文件說明了一個 schema 裡沒有的名稱。使用者確認是哪張表或哪個欄位後，以 `bind_term` 保存。
- **系統狀態**（`system:…`、`policy-validation:…`）：系統處理失敗。把 `missing` 如實告訴使用者，其他項目照常處理。

## 4. 轉交使用者的回答

使用者回答後：

1. 呼叫 `submit_answer`，照錄你問的問題與使用者的原話；回答的是某個待補項目時，帶它的 `item_id`。回答存成一份回答文件並記下回答的使用者，回覆給它的 `upload_id` 與回答所在的行。
2. 回答說了知識時，把它當成一份文件：以這個 `upload_id` 提交產物，以行號引用回答。哪些項目在回答文件上補、哪些要回到原本那份文件上補，照該項的 `closes_with`。
3. 再查一次 `pending_items`，確認這一項已經補上。

只轉交使用者實際說的話；使用者沒有回答的問題維持待補。
使用者授權你自行讀取來源補齊時，同樣以 `submit_answer` 保存你讀到的內容與讀取位置，做法照它的工具說明。

## 5. 補齊一個項目

1. 這個 session 還沒讀過協定時，以 `read_task`（`target` 為 `document`）讀完。
2. 照這一項的 `closes_with`，在說明所缺內容的那份文件上提交缺的產物，帶那份文件的 `upload_id`（以 `run_status` 帶 `uploads` 為 true 查）與出處。要重讀原文時用 `read_document`。
3. 提交被擋下時，這一筆什麼都沒留下：照回覆處理後重送。
4. 再查一次 `pending_items`：這一項不在了就是補上了；還在就看它現在缺什麼。

項目多時，每份文件的項目交給一個子代理，交接寫明項目的內容、那份文件的 `upload_id` 與本節；要問使用者的問題交回主代理一次問。
原文或回答確實寫不成產物的項目留在待補，最後連同原因告訴使用者。

## 6. 使用者指正翻譯或對應

使用者看了翻譯（`read_translation`）或在 Commit 頁看到某條規則有問題時，照 [文件分析](../plasma-document-analysis/SKILL.md) 的「請使用者確認翻譯」處理。

指正的是已發布的資料對應（概念對錯欄位）時，以 `withdraw_mapping` 撤回那筆對應，請使用者在 Commit 頁發布撤回，再執行一次對應。重新上傳同一份文件不會改變對應。

## 7. 完成

再查一次 `pending_items`，然後請使用者到 Commit 頁（`setup.commit_page`）依文件檢視、勾選、預覽並確認發布；發布由使用者在頁面上操作。`setup.commit_page` 是空的時，告訴使用者伺服器沒有設定 Commit 頁網址，請管理員設定。

這次補上了什麼、仍待補的項目與原因、等使用者裁決的項目，如實列給使用者；`later` 的項目也一起列出。
